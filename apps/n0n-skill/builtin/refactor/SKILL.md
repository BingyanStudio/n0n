# Refactor 方法论

## 流程总则

每一步的退出条件是：**能提交一份满足该步格式的 `progress(working)` 报告**。

如果你在整理报告时发现某个字段填不上，说明该步骤没做到位——回退继续工作，直到能完整填写后重新提交。

重构的唯一目标：改善代码结构，不改变外部行为。

---

## 1. 理解现状

**行动**：
- 读懂当前代码的完整意图和边界
- 识别所有调用方（`rg` 搜索所有引用）
- 理解为什么当前代码长这样——可能有历史原因

**退出 → 提交 `progress(working)`，格式：**

```
【阶段】理解现状
【代码意图】（这段代码在做什么）
【调用方】（N 处引用，列出关键消费者）
【历史原因】（为什么写成现在这样）
【风险点】（重构可能影响的边界 / 隐含耦合）
```

填不上"历史原因"？→ 继续 git log 调查。
填不上"风险点"？→ 扩大搜索范围，检查是否遗漏了调用方。

---

## 2. 定义目标

**行动**：回答——重构后应该长什么样？好处是什么？

有效动机：消除重复（3+ 处相同逻辑）、模块解耦、接口简化、类型安全。
**无效动机**："看起来不够干净"（主观）、"未来可能需要"（投机）、单次使用的代码。

**退出 → 提交 `progress(working)`，格式：**

```
【阶段】定义目标
【重构动机】（具体问题是什么——重复/耦合/接口混乱/类型不安全）
【排除的无效动机】（确认不是为了"干净"或"未来需求"）
【目标结构】（重构后代码应该长什么样）
【预期好处】（具体的、可验证的改善）
```

"排除的无效动机"填不上？→ 审视自己的动机是否真的是有效的，还是在做投机重构。

---

## 3. 建立安全网

**硬约束**：先有测试再重构——没有安全网的重构是赌博。

**行动**：
- 确认测试覆盖情况
- 判断是否需要先补测试
- 确认 TypeScript 类型系统能捕获哪些错误

**退出 → 提交 `progress(working)`，格式：**

```
【阶段】建立安全网
【测试覆盖】（哪些部分有覆盖，哪些没有）
【补测试决策】需要补 / 不需要（依据是什么）
【类型系统保护】（哪些错误能被 tsc 捕获）
```

---

## 4. 执行重构

**硬约束**：
- 每个 commit 只做一种类型的变更（rename、move、extract、inline）
- 每步都能通过 typecheck
- 不混合重构和功能变更

**行动**：小步前进，逐步改造。

本步骤可能包含多轮小改动，不需要每轮都提交 progress。在整体改造完成后提交一次。

**退出 → 提交 `progress(working)`，格式：**

```
【阶段】执行重构
【改动概要】（做了哪些结构性调整）
【步骤分解】（拆成了几步，每步做了什么类型的变更）
【中间验证】（每步 typecheck 是否通过）
```

---

## 5. 验证等价

**硬约束**：
- typecheck 通过
- 所有现有测试通过
- 手动检查 git diff 确认没有行为变更
- 公开接口变更时搜索所有消费者确认兼容

**退出 → 提交 `progress(working)`，格式：**

```
【阶段】验证等价
【typecheck】通过 / 失败
【测试结果】全部通过 / 哪些失败
【diff 检查】确认无行为变更 / 发现疑点（说明）
【消费者兼容】（如涉及公开接口：列出消费者和确认情况）
```

有失败项？→ 回到步骤4修正，然后重新提交本步骤报告。

---

## 6. 检查遗漏

**行动**：
- 文档是否需要更新
- 注释是否仍然准确
- 是否有 TODO 可以顺带清理

**退出 → 提交 `progress(completed)`**，包含：重构动机、改动概要、验证结果、遗留事项。
