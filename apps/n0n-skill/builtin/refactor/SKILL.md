# Refactor 方法论

## 原则

重构的唯一目标：改善代码结构，不改变外部行为。

## 流程

### 1. 理解现状

- 读懂当前代码的完整意图和边界
- 识别所有调用方（`rg` 搜索所有引用）
- 理解为什么当前代码长这样——可能有历史原因

### 2. 定义目标

回答：重构后的代码应该长什么样？好处是什么？

常见动机：
- 消除重复（3+ 处相同逻辑）
- 模块解耦（过大的文件、循环依赖）
- 接口简化（参数过多、返回值不清）
- 类型安全（用枚举替代布尔标志）

**不是有效动机**：
- "看起来不够干净"（主观）
- "未来可能需要"（投机）
- 单次使用的代码（不需要抽象）

### 3. 建立安全网

重构前必须确认：
- 有哪些测试覆盖了要改的代码？
- 如果没有测试，是否需要先补充？
- TypeScript 类型系统能捕获哪些错误？

### 4. 小步前进

- 每个 commit 只做一种类型的变更（rename、move、extract、inline）
- 每步都能通过 typecheck
- 避免同时修改接口和实现

### 5. 验证等价

- typecheck 通过
- 所有现有测试通过
- 手动检查 git diff 确认没有行为变更
- 如果重构涉及公开接口，搜索所有消费者确认兼容

### 6. 检查遗漏

- 文档是否需要更新？
- 注释是否仍然准确？
- 是否有 TODO 可以顺带清理？

---

## 硬约束

- **先有测试再重构** — 没有安全网的重构是赌博
- **不混合重构和功能变更** — 一个 PR 只做一件事
- **不删除看似无用的代码** — 标记 `// XXX:` 而不是直接删除
- **保持 git history 可读** — 小步 commit，message 说清意图

## 流程与汇报节点

在以下判断节点用 `progress(working)` 汇报你的决策和依据：

### 理解现状后

汇报：当前代码的意图是 X，调用方有 N 处，历史原因是 Y。判断重构可行 / 存在风险点 Z。

### 定义目标后

汇报：重构动机是 X（排除了"仅为美观"等无效动机），目标结构是 Y，预期好处是 Z。

### 建立安全网后

汇报：测试覆盖情况——A 部分有覆盖，B 部分无覆盖（判断是否需要先补测试，及依据）。

### 验证等价后

汇报：typecheck 通过 / 测试通过 / diff 确认无行为变更。如有疑点说明。

最终用 `progress(completed)` 提交完整报告。
