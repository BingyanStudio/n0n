# Bugfix 方法论

## 流程总则

每一步的退出条件是：**能提交一份满足该步格式的 `progress(working)` 报告**。

如果你在整理报告时发现某个字段填不上（比如"排除了什么"想不出来、"依据"不充分），说明该步骤没做到位——回到上一步继续工作，直到能完整填写后重新提交。

回退不是错误，而是质量保障的自然机制。

---

## 1. 格物定位

> 格物致知。物格而后知至。

**硬约束**：不要执行任何修改。不要跳过这一步直接编码。

**行动**：
- 探索代码、日志、复现路径
- 明确问题的实体和边界
- 区分：这是 bug？设计缺陷？还是未满足的需求？

**退出 → 提交 `progress(working)`，格式：**

```
【阶段】格物定位
【问题定义】（一句话说清问题是什么）
【期望状态】（A₁ 应该是什么）
【实际状态】（A₀ 观察到什么）
【判断依据】（凭什么认为问题是这个）
【排除项】（排除了哪些其他可能，为什么）
```

填不上"排除项"？→ 说明探索不够充分，继续调查。

---

## 2. 红灯复现

**行动**：构造最小复现路径，确认问题可稳定触发。

**退出 → 提交 `progress(working)`，格式：**

```
【阶段】红灯复现
【复现结果】已复现 / 无法复现
【复现路径】（具体步骤或命令）
【观察到的错误】（具体输出/行为）
```

无法复现？→ 回到格物定位，重新审视问题定义是否正确。

---

## 3. 对齐标准

**硬约束**：不要在没有评估标准的情况下开始执行。

**行动**：
- 定义验收条件（可验证的 true/false 信号）
- 确定每个条件的观测方式
- 如果涉及用户主观判断，用 `progress(blocked)` 请求确认

**退出 → 提交 `progress(working)`，格式：**

```
【阶段】对齐标准
【验收条件】
  1. （条件1 — 如何验证）
  2. （条件2 — 如何验证）
  ...
【失败回溯路径】（如果验证不通过，往哪个方向排查）
```

如需用户确认 → 改用 `progress(blocked)`，在 blocked 中完整展示你的问题理解和拟定的验收条件。

---

## 4. 追溯根源

**行动**：
- `git blame` 追溯引入 bug 的 commit
- 理解原始意图——代码为什么写成这样
- 定位根因而非表象

**退出 → 提交 `progress(working)`，格式：**

```
【阶段】追溯根源
【根因判断】（根本原因是什么）
【引入点】（哪个 commit / 什么时候引入的）
【原始意图】（当时为什么这样写）
【排除项】（排除了哪些其他根因假设，为什么）
```

填不上"原始意图"？→ 继续 git log / blame 调查。
填不上"排除项"？→ 只有一个假设时需要追问自己：这个假设是否真的没有替代解释？

---

## 5. 尝试修复

**硬约束**：
- 先读后改——不理解上下文不动代码
- 每一轮尽可能批量发出工具调用
- 最小改动原则

**退出 → 提交 `progress(working)`，格式：**

```
【阶段】尝试修复
【修复方案】（做了什么改动）
【选择依据】（为什么选这个方案）
【排除方案】（考虑过但排除的方案，及原因）
```

只有一种合理修复方式、无需选择？→ 该字段填"无合理替代方案"即可，不必强造。

---

## 6. 绿灯验证

**硬约束**：
- 用实际执行验证，不用臆想
- 如实报告——绝不伪造通过或隐藏失败

**退出 → 提交 `progress(working)`，格式：**

```
【阶段】绿灯验证
【验证结果】全部通过 / 部分失败
【验收条件逐项】
  1. ✓/✗ （实际观察）
  2. ✓/✗ （实际观察）
  ...
【失败处理】（如有失败：原因判断 + 下一步方向）
```

有失败项？→ 回到步骤5重新修复，然后重新提交本步骤报告。

---

## 7. 横向排查

**硬约束**：横向排查不是可选项——必须执行。

**行动**：
- 项目中相似的位置是否存在同类问题
- 一旦发现一处，逐一排查并修复

**退出 → 提交 `progress(working)`，格式：**

```
【阶段】横向排查
【搜索范围】（搜了什么、用了什么命令）
【发现】N 处同类问题 / 确认无同类问题
【处理】（逐一说明修复情况，或说明为什么确认不存在）
```

---

## 8. 请求验收

提交 `progress(completed)`，包含完整修复报告：问题、根因、修复方案、验证结果、横向排查结果。
