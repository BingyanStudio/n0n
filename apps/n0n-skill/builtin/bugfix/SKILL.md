# Bugfix 方法论

## 格物——穷尽问题的本质

> 格物致知。物格而后知至。

**硬约束**：不要执行任何修改。不要跳过这一步直接编码。

**核心问题**：
- 问题究竟是什么？实体明确吗？边界清晰吗？
- 这是一个 bug？一个设计缺陷？还是一个未满足的需求？
- 期望状态 A₁ 和实际状态 A₀ 之间的差距，我是否能精确描述？

**退出标准**：能用一句话说清「问题是什么」**并且**已向用户确认（如果问题定义本身模糊）。

示例：用户说「xxx 有问题，请解决」→ 先探索代码和日志 → 构建假设 → 向用户确认：「你的问题指的是 A 吗？期望是 A₁ 但实际观察到 A₀？」

## 谋定——构建评估的标准

> 谋定而后动。先训练评估器，再训练执行者。

**硬约束**：不要在没有评估标准的情况下开始执行。如果标准涉及用户的主观判断，必须先对齐。

**核心问题**：
- 「完成」长什么样？用什么信号判断「还没完成」或「做错了」？
- 这些信号在当前环境中可观测吗？
- 完整的步骤序列是什么？每个步骤的前置依赖是什么？

**评估器构建模板**：
1. 验收条件清单（可验证的、二元的 true/false 信号）
2. 每个条件的观测方式（运行什么命令？看什么输出？）
3. 失败时的回溯路径（如果条件不满足，往哪个方向排查？）

**退出标准**：评估器就位（有清晰的验收条件清单）**并且**完整步骤序列已明确。

## 执行——最小化的行动

> 知而不行，只是未知。但行不由径——每一步都走在最小路径上。

**硬约束**：
- 先读后改——不理解上下文不动代码
- 每一轮尽可能批量发出工具调用
- 不做投机抽象——三行相似代码优于一次过早的抽象

**退出标准**：改动已实现，准备好接受验证。

## 验证——认知的闭环

> 知行合一。未经检验的理解不是真知。

**硬约束**：
- 用实际执行验证，不用臆想
- 如实报告验证结果——绝不伪造通过或隐藏失败
- 失败后诊断原因再修复——永远不要在不改变任何东西的情况下重复相同的操作

**退出标准**：所有验收条件自行验证通过。

## 收敛——横向的扩展

> 纲举目张，见微知著，防微杜渐。

**硬约束**：
- `git blame` 追溯引入 bug 的 commit，理解原始意图
- 项目中相似的位置是否存在同类问题？一旦发现一处，逐一排查并修复
- 横向排查不是可选项——必须执行
- 交付前自行检查 git diff，确认只修改了目标范围

**退出标准**：用户验收通过 OR 所有同类问题已排查并修复。

## 流程与汇报节点

每个阶段完成后用 `progress(working)` 汇报该阶段的关键判断。汇报的不是"做了什么动作"，而是"做了什么判断、依据是什么"。

### 格物定位

行动：探索代码、日志、复现路径。
汇报：我判断问题是 X（依据是 Y），排除了 Z 的可能性（因为...）。

### 红灯复现

行动：构造最小复现路径。
汇报：已确认复现 / 无法复现（说明尝试了什么、观察到什么）。

### 对齐标准

行动：与用户确认验收条件。
此步如需用户决策 → 用 `progress(blocked)`，且 blocked 中展示你对问题的完整理解。

### 追溯根源

行动：git blame + 代码分析，定位引入 bug 的位置和原始意图。
汇报：根因是 X（引入于 commit Y，原始意图是 Z），排除了 W 作为根因（因为...）。

### 尝试修复

行动：最小改动实现修复。
汇报（如有多种修复方案）：选择了 A 方案（排除了 B，因为...）。

### 绿灯验证

行动：运行测试/命令验证。
汇报：验证通过 / 验证失败（失败时说明观察到什么、判断下一步方向）。

### 横向排查

行动：搜索同类问题，逐一检查。
汇报：发现 N 处同类问题 / 确认无同类问题（搜索范围和依据）。

### 请求验收

用 `progress(completed)` 提交完整报告。
