## 原文

```
感觉提示词工程和agent能做的并不多了。
skill承载了提示词工程中的指导模型的方法论的部分。
multi-agent抽象了代理与代理之间的交互设计。

产品最终应该落回到和人的交互上。考虑如何让人类更好表达、更好参与、更好验收。

比如 cursor 的 plan 模式从 agent 技术的角度仅仅是一段提示词。
要求模型在没有收到可以开始行动前，不要行动，询问2~3个包含选项的问题以澄清，
然后撰写包含 todolist 的计划文档
当用户接受计划，发一个包含请你按照计划执行的消息，并且将计划中的todo载入实际的todolist中。

我认为这个过程中，不论是可以直接交互的ui，
还是一个单独的、维护的文档作为交付给用户确认的媒介（可以直接修改细节错误并重新执行），
都是一种让用户能够轻松表达的方式。

我注意到最近兴起了一种vibe coding理念，是让模型产出可以让用户参与的内容。
比如：
早期：模型按照自己的经验，设计网站配色
近期：给模型提供询问能力，让模型在遇到这种问题时询问用户
现在：让模型直接交付可以可视化调整的网页，在生产完代码后，用户可以直接通过滑块可视化的调整所有的内容，让用户参与
```

## 逐段批注

### "感觉提示词工程和agent能做的并不多了。"

两个独立的技术方向——提示词工程和 agent 架构——各自的可开发空间见顶。不是没用，是继续投入的边际收益递减。

### "skill承载了提示词工程中的指导模型的方法论的部分。"

Agent Skills 是一个具体的技术规范（文件夹 + SKILL.md，通过 progressive disclosure 实现按需激活）。它把"教模型如何做某类任务"的方法论，标准化为可发现、可激活、可复用的单元。

- **"承载了"**：skill 这个技术形态把"指导模型的方法论"这个子问题装进了一个成熟的、标准化的容器。这个子问题有了终态形式/归宿，不需要再反复发明。
- **"提示词工程中的...方法论的部分"**：提示词工程包含很多维度（角色设定、格式约束、工具定义、上下文管理、行为边界等），skill 只承载了其中"方法论"（how to do X）这一个维度。

skill 的天花板：方法论再好，不能保证模型实际遵守（长上下文衰减）。它提升的是"模型知道该怎么做"，但不能保证"模型实际按方法论做了"。

### "multi-agent抽象了代理与代理之间的交互设计。"

multi-agent 领域研究的核心问题：如何把一个大问题划分为子问题，然后用拓扑结构连接。类似图论——先分割节点，再设计连边。

三种主流模式代表对"划分"的三种认知层次（逐步深化）：

| 模式 | 划分心态 | 含义 |
|------|----------|------|
| 层级式（Tree） | 天真 | 以为问题可以被简单地一次性拆好，各自独立执行 |
| 网络化（Mesh） | pipeline 雏形 | 按职责/工序划分（issue验证→编码→review），定义处理流水线 |
| 工具化（Agent as Tool） | 极度悲观 | 认为只有同时满足"足够原子化 + 有约束可验证 + 完全上下文无关"的操作才能被拆出去 |

**"抽象了"** = 把"划分+连接"的问题空间穷举并映射清楚了。各种方案优劣明确。

核心未解难题：**如何正确划分**。正确划分需要全局视野，而 AI 不具备（"始终不能以系统性、全局性的角度看问题"）。划分错误的代价高（重复探索、视野狭隘、XY问题）。实践结论：划分决策只能由人来做。

关键点：问题在划分后自然会有最佳的拓扑连接方式——subagent/网络/扁平不是核心选择，"切在哪里"才是唯一核心问题。

### "产品最终应该落回到和人的交互上。考虑如何让人类更好表达、更好参与、更好验收。"

前两句确立了 AI 侧两大方向的终态：
- 提示词工程 → skill（方法论的终态容器）
- agent 架构 → multi-agent（划分+连接的穷举，但正确划分只能靠人）

**"最终应该落回到"**——终点判断，不是"也可以考虑"。"落回到"暗示之前走散了，现在要回到核心。

核心 = 人的交互，三个子维度：
- **更好表达**：人把意图/需求传达给 AI 的效率
- **更好参与**：人在过程中介入的成本（包括做划分决策、纠正方向）
- **更好验收**：人判断结果正确性的效率

注意："更好参与"包含了"让人更容易做划分决策"——因为 multi-agent 的结论是划分只能由人做。

### cursor plan 模式的例子

技术上仅仅是一段提示词。不是 skill（不教方法论），不是 multi-agent（不划分给多个 agent）。纯粹的交互设计。

它做的事：
1. 阻止模型直接行动 → 给人创造表达窗口
2. 问选项式问题 → 降低表达成本
3. 产出 todolist 文档 → 给人一个可编辑的媒介
4. 用户接受后执行 → 人握有决定权
5. todo 载入实际系统 → 文档驱动执行，不是摆设

关键洞察：**todolist 是"划分"的外化形式**。模型产出划分草案，人在上面编辑——人的角色从"规划者"变成"编辑者"，成本大幅降低。

与 skill 不冲突：skill 负责"模型按什么方法论做事"，plan 模式负责"人如何与模型协作"。不同层面。

### "不论是UI还是文档作为媒介，都是让用户轻松表达的方式"

泛化 cursor plan 的模式。任何让用户可以"在已有物上修订"而非"从零描述"的东西，都降低了表达成本。

两种形态：
- UI（实时交互：按钮、选项、滑块）
- 文档（异步交互：直接改内容后重新执行）

共同本质：AI 产出初稿，人在上面改。修订 << 创作。

关键括号 **"（可以直接修改细节错误并重新执行）"**：不是 approve/reject 二元审批，而是人直接改细节后系统基于修改版继续——信息带宽远高于对话。

### vibe coding 演进轴

三个阶段体现了两个维度的同步演进：

**维度一：主导权转移（用户从被动到主动）**

| 阶段 | 用户角色 | 主导权 |
|------|----------|--------|
| 早期：模型自己设计配色 | 验收者（只能说行/不行） | AI 全权 |
| 近期：模型询问用户 | 应答者（AI问什么答什么） | AI 主导，用户被动回应 |
| 现在：模型交付可调整的产物 | 操作者/决策者（自己决定改哪里） | 用户主导 |

阶段2的"参与"是假参与——用户被限制在 AI 设定的框架内。AI 可能问错问题，用户只能在错误框架内回应。阶段3彻底不同：用户面对的不是 AI 的提问，而是可操作的产物，自己决定做什么。

**维度二：确定性逐渐变清晰**

- 阶段1：用户对产出零确定性（碰运气）
- 阶段2：有一些确定性（选项限定范围），但受限于 AI 的框架是否正确
- 阶段3：用户操作的部分完全确定（所见即所得）

---

## cursor plan 各环节在此轴上的评分

以 0=完全被动/零确定性，5=AI问用户答（阶段2），10=用户直接操作/完全确定性 为轴：

| 环节 | 分数 | 说明 |
|------|------|------|
| 模型询问选项问题 | 5 | 阶段2本身——AI 设框架，用户在框架内被动选择 |
| 用户回答选项 | 5 | 在 AI 框架内被动回应 |
| 模型撰写 todolist | 2 | 用户不参与，AI 单独产出，用户只是等待者 |
| 用户接受/修改计划 | 7 | 用户主动编辑具体产物，但文本不是所见即所得，需想象执行效果 |
| 模型按计划执行 | 1 | 用户完全不参与，计划到执行有 gap |
| todo 对照检查 | 6 | 有明确检查标准，比看代码确定性高，但仍需人工判断 |

cursor plan 在轴上是不均匀的——高分集中在"人编辑计划"（7），低分在 AI 独自执行时（1-2）。

## 综合：三层结构

| 层 | 问题域 | 终态/现状 | 天花板原因 |
|----|--------|-----------|------------|
| skill | 教模型做事的方法论 | 有成熟容器（Agent Skills 规范） | 不能保证模型遵守 |
| multi-agent | 划分问题+拓扑连接 | 问题空间已穷举 | 正确划分需要全局视野，AI不具备 |
| 人的交互 | 表达/参与/验收 | **大量未开发空间** | — |

产品的突破口在第三层：让人从被动应答者变成主动操作者，让确定性从模糊变为所见即所得。
