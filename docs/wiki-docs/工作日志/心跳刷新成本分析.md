# 心跳刷新成本分析

> 结论词条：【心跳策略】
> 配套可视化：[opus-4.6-heartbeat-chart.html](../../analysis/opus-4.6-heartbeat-chart.html)

## 背景

【提示词缓存】TTL 为 5 分钟。【心跳策略】在 TTL 到期前发送轻量请求刷新缓存前缀，主要服务于用户在场但未发消息的场景（读代码、验收）。

## 定价模型

每个输入 token 按且仅按一种费率计价（三选一，不叠加）：

| 场景 | 费率 |
|------|------|
| 缓存命中（心跳/正常请求） | Cache Read = $0.50/MTok |
| 缓存未命中（首次/过期后重建） | Cache Write = $6.25/MTok |
| 不使用缓存 | Input = $5/MTok |

## 推导

### 纯线性模型

```
单次心跳成本     = prefix × $0.50/MTok
Cache miss 额外  = prefix × ($6.25 - $0.50) = prefix × $5.75/MTok
盈亏平衡次数 N   = $5.75 / $0.50 = 11.5 次 ≈ 52 分钟（4.5min 间隔）
```

prefix 在分子分母中约掉——盈亏平衡与前缀大小无关。

### 修正模型（加入固定开销）

```
单次心跳成本     = prefix × $0.50/MTok + C_fixed
盈亏平衡次数 N   = (prefix × 5.75) / (prefix × 0.50 + C_fixed)
```

C_fixed（约 $0.005，~1000 非缓存 token）打破线性对称：前缀越小，甜蜜点越早。

| 前缀 | 盈亏次数 | 盈亏时间（4.5min 间隔）|
|------|---------|----------------------|
| 10K  | 5.8 次 | ~26 min |
| 50K  | 9.6 次 | ~43 min |
| 100K | 10.5 次 | ~47 min |
| 200K | 11.0 次 | ~49 min |
| ∞    | 11.5 次 | ~52 min（理论极限）|

### 有界损失验证

以 100K 前缀为例：

| | 成本 |
|--|------|
| 10 次心跳 | $0.500 |
| 1 次 miss 额外成本 | $0.575 |
| 比值 | 0.87 |

跑满 10 次心跳的开销仍低于一次 cache miss 的额外成本。

### 跨模型比例

| 模型 | Cache Read | Cache Write | 理论 N |
|------|-----------|-------------|--------|
| Opus 4.6 | $0.50 | $6.25 | 11.5 |
| Sonnet 4 | $0.30 | $3.75 | 11.5 |
| Haiku 3.5 | $0.03 | $0.30 | 9.0 |

各模型盈亏次数接近，策略通用。
