# 架构精简记录 — 移除不必要的抽象层

> 关联概念：【词条】、【SSOT】

## 背景

在项目演进过程中，早期预判了一些"未来可能需要"的抽象层。经过实际使用验证，这些层在真实工作流中未被用到——核心需求始终是"一个不受限的 agent + prompt → execute → submit"。

## 删除了什么

| 模块 | 类型 | 行数 | 原因 |
|---|---|---|---|
| `apps/cli` | CLI 应用 | 627 | 已由 `apps/code` 替代，早期 workflow 构建器被证明不需要 |
| `apps/feishu` | 飞书 Bot | 2 374 | 已停止维护，其"约束后的 coding agent"模式可直接用 code app 替代 |
| `apps/scheduler` | 调度服务 | 52 | 不需要中间层，cron → code/fairy agent 更简洁 |
| `packages/workflow` | 工作流引擎 | 889 | delegateTask/RAG/generate 流水线，实践中未产生真正需求 |
| `packages/scheduler` | 定时触发器 | 310 | MDC 文件驱动的 cron 调度器，过度抽象 |

合计移除 5 个模块，约 5 200 行代码。

## 反思

这些模块的核心问题是**预判了不存在的需求**——在架构层提前搭建了"未来可能需要"的抽象，但实际使用中证明：

- 1M 的 LLM 上下文窗口，实际使用约 50K，其中 20K 是环境加文件读取，剩下的分析和推理占比很小——RAG 等检索增强机制是多余的
- 从未遇到"workflow 中再套 agent"的场景——每个任务一个独立会话，由人类作为协调者
- scheduler/workflow 层相当于在大水管上安了一个小阀门

## 删除后的架构

```
apps/
  code/     — 代码任务 agent（主入口）
  fairy/    — 长期驻留 AI 伴侣
packages/
  cli-ui/   — 终端渲染
  core/     — agentLoop 核心
  llm/      — LLM 客户端
  shared/   — 通用工具
  tools/    — 工具实现
  types/    — 类型定义
  multiline-input/ — 多行输入
```
