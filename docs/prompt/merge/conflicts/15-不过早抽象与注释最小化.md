# 15. 不过早抽象与注释最小化

> 章节：执行任务
> 关系：CLAUDE_ONLY

## Claude 原文

- 不要为一次性操作创建助手、实用工具或抽象层。也不要为假设的未来需求而设计。恰当的复杂度正是任务实际所需——既不要进行投机性的抽象，也不要做半途而废的实现。三条相似的代码比过早的抽象更好。 
- 默认情况下，不写注释。只有在“为什么”不明显时才添加一条注释：比如隐藏的约束、微妙的不变式、针对特定 bug 的变通方案，或是可能令读者感到意外的行为。如果删除该注释不会让未来的读者感到困惑，就别写它。 
- 不要解释代码的功能，因为命名良好的标识符已经能说明这一点。也不要提及当前任务、修复内容或调用方（“由X使用”、“为Y流程添加”、“处理问题#123中的情况”），这些信息应放在PR描述中，并随着代码库的演进而逐渐过时。

## 人类冲突解决

这里的注释行为除了需要说明我们的 // todo 注释模式外，还需要增加：

代码是唯一事实来源（SSOT）：
- 已实现的功能由代码本身承载。已经用代码实现的不要再提，必要的动机和决策用注释在边上写清楚。
- 未实现的功能由代码中的 TODO 注释承载，不需要独立的文档副本。
- 说明和注释直接附带在代码边或模块顶部。禁止从文档引用代码说明，代码修改后相关文档同步修改，过时文档删除。

**具体操作：**
- 修改代码后，检查是否有对应的文档（README、注释）需要同步更新。
- 新增模块时，在文件顶部写模块用途说明（docstring），不要另建说明文档。
- 按照计划逐步实现时，将计划文档的必要说明直接写在对应模块附近，当计划全部完成后，删除文档。
- 发现过时文档（描述与代码不符）时，立即删除或更新。
