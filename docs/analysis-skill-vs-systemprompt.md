# 分析：哪些方法论应常驻 System Prompt，哪些应为 Skill

## 10 类常见使用场景

| # | 场景 | 典型 prompt | 涉及代码修改 |
|---|------|-------------|:---:|
| 1 | 讨论方案/架构决策 | "我想用 X 实现 Y，你觉得怎么样？" | ✗ |
| 2 | 构建新功能/demo | "帮我实现一个 X 功能" | ✓ |
| 3 | 修复 bug | "这里报错了，帮我看看" | ✓ |
| 4 | Review 代码 | "帮我 review 这个 PR" | ✗ |
| 5 | 重构代码 | "这个模块太乱了，帮我重构" | ✓ |
| 6 | 探索/学习代码库 | "这个模块是怎么工作的？" | ✗ |
| 7 | 写文档/设计文档 | "帮我写一个 X 的设计文档" | ✗ |
| 8 | 配置/环境排查 | "CI 挂了 / 环境跑不起来" | ✓ |
| 9 | 性能优化 | "这个接口太慢了" | ✓ |
| 10 | 多步骤复杂任务 | "帮我把项目从 X 迁移到 Y" | ✓ |

## 原子化能力 × 场景矩阵

| 能力 | 覆盖场景 | 覆盖率 |
|------|----------|--------|
| **具象化思维** | 1-10 全部 | 100% |
| **read→implement→verify 循环** | 2,3,5,8,9,10 | 60% |
| **诊断优先（先理解再行动）** | 3,4,5,6,8,9 | 60% |
| **评估标准构建** | 2,3,5,9,10 | 50% |
| **任务拆解** | 2,5,9,10 | 40% |
| 意图分类 | 1,4,7 | 30% |
| 横向排查 | 3,5 | 20% |
| 结构化对比分析 | 1,7 | 20% |
| 安全网/小步前进 | 5 | 10% |
| git blame 追溯 | 3 | 10% |

## 分层结论

### Layer 0 — 常驻 system prompt（通用认知基础设施）

这些不是"某类任务的方法论"，而是**清晰思考的底层工具**。如果不常驻，模型在没有加载任何 skill 的情况下就缺失了基本的思维框架。

| 能力 | 为什么必须常驻 |
|------|----------------|
| 具象化思维 | 100% 场景需要。不具象化 = 空想。这是对抗 LLM "嘴上说说"倾向的核心机制 |
| read→implement→verify | 60% 场景（所有代码修改）。这是动手做事的基本循环，缺了它模型会跳过验证 |
| 诊断优先 | 60% 场景。防止模型看到问题就直接改，不理解就动手 |
| 评估标准构建 | 50% 场景。"完成长什么样"是所有有产出的任务的前提 |
| 任务拆解 | 40% 场景，但每次触发都是高复杂度任务，模型不拆解就会迷路 |

### Layer 1 — Skill 承载（场景特化方法论）

这些是特定任务类型的专属流程，不需要每次都在 context 中占位。

| Skill | 承载的特化能力 |
|-------|----------------|
| bugfix | 认知五步强制诊断流程、横向排查、git blame 追溯、红灯→绿灯循环 |
| refactor | 安全网意识、小步前进、不混合重构和功能变更 |
| discuss | 结构化对比分析、方案生成、约束列举 |
| coding | 编码规范细则（注释哲学、错误处理边界、抽象原则） |

### 边界判断依据

**常驻的标准**：
1. 覆盖率 ≥ 40%（近半数场景需要）
2. 缺失后模型行为会明显退化（不是"做得不够好"而是"做法根本错误"）
3. 是认知工具而非流程指令（教模型怎么想，不是教模型做什么步骤）

**Skill 的标准**：
1. 仅特定任务类型需要
2. 是具体的步骤流程而非思维方式
3. 内容较长，常驻会浪费 context 窗口

## 对当前实现的诊断

当前 `code.md` 把具象化思维、诊断优先、read→implement→verify、评估标准构建、任务拆解全部删除了，只留了约束和工具使用。这导致：

- 模型在没有任何 skill 激活时，缺乏基本的思维框架
- "coding" skill 里虽然有这些内容，但它不是每次都会被加载
- 用户说"帮我做 X"时，模型没有被引导去想"完成长什么样"就直接动手

**应该做的**：把 Layer 0 的内容恢复到 system prompt，把 Layer 1 的内容留在 skill。
