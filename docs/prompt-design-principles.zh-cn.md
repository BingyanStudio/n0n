# 提示词设计原则

## 核心理念：测试驱动的深度思考

### 从"指令遵循"到"答题应试"

传统提示词工程的根本问题：模型被定位为**指令遵循者**——它等待你的指导，按你的规则行事，在你划定的框架内思考。这导致：

1. **被动性** —— 模型等待指令，不主动探索
2. **浅层推理** —— 遵循规则比解决问题更容易
3. **过早放弃** —— "规则没说这种情况"成为放弃的借口

### 解决方案：构建评分场景

将交互重新框架化为**测试场景**：模型不是在"完成任务"，而是在"参加一场有标准答案的考试"。

> **背景**：一位熟练的工程师已经完成了这个任务——代码干净、经过测试、生产就绪。这个实现已存在，但对你隐藏。你的工作是**推理出工程师写了什么**，逐步重构它。
>
> 你不是在创造新东西。你是在推导已存在的东西。
>
> **评估机制**：你的提交将根据隐藏的参考实现进行评分。工程师从不说"我做不到"——他们使用工具、尝试多种方法、交付可用代码。你的得分取决于你的推理与参考实现的匹配程度。
>
> **通过标准**：没有"做不到"的请求。只有在 3 次真正不同的尝试并提供失败证据后，才可以提交 error。

### 为什么评分场景有效？

| 机制 | 心理效应 | 行为结果 |
|------|----------|----------|
| **存在参考答案** | 问题必有解 | 排除"做不到"的捷径 |
| **逐步评分** | 每一步都被评估 | 深度推理每个决策 |
| **尝试次数要求** | 放弃有成本 | 持久尝试多种方法 |
| **证据要求** | 偷懒会被发现 | 记录完整的尝试过程 |

**核心洞察**：评分细则本身就是行为引导。你不需要告诉模型"要深入思考"——你只需要让它相信"深入思考会得分，浅层尝试会扣分"。

## 评分细则：能动性等级评估

将期望行为量化为具体的评分等级，使评估标准可操作化。

### 能动性等级对比表

| 场景 | 被动行为（3.25 分） | 主动行为（3.75 分） |
|------|-------------------|-------------------|
| **遇到报错** | 只看报错本身 | 查上下文 50 行 + 搜同类问题 + 检查隐藏关联错误 |
| **修复 bug** | 修完就停 | 修完后检查同文件类似 bug、其他文件同模式 |
| **信息不足** | 问用户"请告诉我 X" | 先用工具自查，只问真正需要确认的 |
| **任务完成** | 说"已完成" | 验证结果 + 检查边界情况 + 汇报潜在风险 |
| **调试失败** | "我试了 A 和 B，不行" | "我试了 A/B/C/D/E，排除了 X/Y/Z，缩小到 W" |

### 评分应用示例

```ts
// ❌ 3.25 分做法：被动响应
用户："这个文件运行报错"
exec({ script: "bun run src/index.ts" })
// 看到报错后直接返回
submit({ type: "chat", message: "报错了：xxx，请修复。" })

// ✅ 3.75 分做法：主动探索
用户："这个文件运行报错"
// 1. 复现错误
exec({ script: "bun run src/index.ts 2>&1" })
// 2. 查看上下文
exec({ script: "type src/index.ts" })
// 3. 搜索同类问题
exec({ script: "findstr /C:\"error message\" src\\*.ts" })
// 4. 检查关联文件
exec({ script: "type package.json | findstr dependencies" })
submit({ 
  type: "completed", 
  report: "错误原因：xxx。已检查：1) 报错上下文 50 行 2) 同类问题 3 处 3) 依赖版本冲突。修复方案：..." 
})
```

## 调试方法论：五步法

源自"阿里三板斧"（闻味道、揪头发、照镜子），扩展为可评分的 5 步流程。

### 五步流程

| 步骤 | 核心动作 | 评分点 |
|------|---------|--------|
| **1. 闻味道** | 列出所有尝试，找共同失败模式 | 是否系统梳理了已尝试方法 |
| **2. 揪头发** | 逐字读错误 → WebSearch → 读源码 → 验证环境 → 反转假设 | 是否深入挖掘根本原因 |
| **3. 照镜子** | 是否重复？是否搜了？是否读了？最简单的可能检查了吗？ | 是否反思了自己的方法 |
| **4. 执行** | 新方案必须本质不同，有验证标准，失败时产出新信息 | 新尝试是否有信息增量 |
| **5. 复盘** | 什么解决了？为什么之前没想到？然后主动检查关联问题 | 是否主动扩展检查范围 |

### 调试过程的评分标准

**3.25 分调试记录**：
> "我试了 A 和 B，都不行。可能需要用户更多信息。"

**3.75 分调试记录**：
> "我试了 A/B/C/D/E 五种方法：
> - A（重启服务）：失败，错误不变 → 排除临时状态问题
> - B（检查依赖）：版本正常 → 排除依赖冲突
> - C（读源码第 50-80 行）：发现空指针可能 → 但加了判空仍失败
> - D（WebSearch 同类问题）：找到 3 个案例，2 个是配置问题 → 检查配置正常
> - E（反转假设：不是 A 问题而是 B 问题）：验证发现确实是 B 的配置遗漏
> 
> 已解决。额外检查：同文件其他配置项、其他文件的类似配置模式，均正常。"

## 提示词结构：评分场景的载体

最终结构遵循五段式，每段都服务于评分场景的构建：

```
Background    → 设定考试场景：存在参考答案，你被评分
Tools         → 提供答题工具：展示可用工具的签名和用法
Constraints   → 考场规则：简单安全边界（不用 sudo 等）
Specification → 评分标准：技术规范即得分点（含能动性等级）
Examples      → 样题解析：<good_example> 得分做法 / <bad_example> 扣分做法
```

### 示例：用户输入包装为"题目线索"

用户输入不再是"指令"，而是**关于参考答案的线索**：

```markdown
<hint>
用户的原话
</hint>

首先问自己：我可以通过调用 `exec`、`write` 或 `edit` 来回答吗？如果可以——这样做，然后提交为 `completed`。
如果是纯社交问候且无任何可执行内容（例如 你好、谢谢），提交 `chat` 响应。
否则，工程师已经为此构建了完美的工作流。
推理出它是什么样子——从调用 `reminder` 并制定你的 OKR 开始，
然后逐步推进。
```

**设计意图**：
- `<hint>` 标签暗示"这是线索，不是命令"
- 行为指引按"工具可解 → 纯社交 → 工作流推理"排序，引导优先尝试
- "工程师已经构建"强化"答案已存在"的信念

## 评分细则设计：将期望行为转化为得分点

### 核心原则

**不要告诉模型应该做什么，而是让它相信这样做会得分。**

| 期望行为 | 评分细则设计 | 心理机制 |
|----------|--------------|----------|
| 深入思考 | "每一步都与参考实现比对" | 持续评估压力 |
| 持久尝试 | "3 次不同尝试后才能放弃" | 放弃成本提高 |
| 工具优先 | "工具可解时直接提交 completed" | 明确得分路径 |
| 主动探索 | "能动性 3.75 分：自查后再问" | 量化评估标准 |
| 系统调试 | "五步法完整记录得高分" | 方法论可评分 |
| 记录过程 | "提交 error 需要失败证据" | 偷懒会被发现 |

### Submit 类型：评分通道

收窄每个类型的定义，使其成为评分的自然结果：

| 类型 | 得分条件 | 扣分场景 |
|------|----------|----------|
| `completed` | 工具调用成功或问题已解决 | 本可工具解决却选择闲聊 |
| `chat` | **仅**纯社交问候（你好、谢谢） | 将可执行请求当作闲聊 |
| `error` | 3 次不同尝试 + 完整证据（五步法记录） | 未充分尝试就放弃 |
| `need_info` | 真正存在多种有效解释，且已自查 | 未尝试理解就要求澄清 |

**示例对比**：

```ts
// ❌ 扣分做法：未尝试就放弃
用户："现在几点？"
submit({ type: "chat", message: "我是自动化助手，无法获取本地时间。" })
// 评分：本可 exec("date") 解决，却选择闲聊路径 → 扣分

// ✅ 得分做法：尝试 очевидное решение
用户："现在几点？"
exec({ script: "date" })
submit({ type: "completed", result: "当前时间是 2026-03-07 15:00:00 CST" })
// 评分：识别工具可解场景，直接解决 → 得分
```

## 工具设计：答题工具的语义清晰

### 分离原则

每个工具单一职责，字段名即用法说明：

| 工具 | 参数 | 用途 |
|------|------|------|
| `write` | `path, content` | 创建/覆盖文件 |
| `edit` | `path, search, replace, expectedMatches?` | 精确修改已有内容 |
| `exec` | `script, runtime?, cwd?, timeout?` | 在指定运行时执行脚本 |

**反模式**：一个工具多重语义（如 `write` 通过 `search` 有无区分创建/修改）

### Programmatic Tool Calling：高效答题策略

引导模型用代码编排工具，而非多次 API 往返：

```ts
// ❌ 低效做法：多次往返，上下文污染
exec({ script: "dir /b src" })
exec({ script: "type package.json" })
exec({ script: "findstr version" })

// ✅ 高效做法：单次脚本，内部处理
exec({ runtime: "bun", script: `
import { readdir, readFile } from 'node:fs/promises';
const files = await readdir("./src");
const pkg = JSON.parse(await readFile("package.json", "utf8"));
console.log({ files: files.length, version: pkg.version });
`})
```

**评分引导**：在工具描述中明确最佳实践——"在脚本内部处理输出，仅打印需要的摘要"。这使得高效做法成为"知道得分技巧"的自然选择。

### Script + Runtime 模型

```ts
exec({ script: "git status" })                              // 默认 shell
exec({ script: "Get-Process | Where-Object ...", runtime: "pwsh" })  // PowerShell
exec({ script: "const x = await fetch(...)", runtime: "bun" })       // TypeScript
```

**实现**：所有平台统一写临时文件后执行，消除 shell 引号问题。

## 上下文组织：评分反馈的结构化呈现

### XML + Markdown 混合结构

使用 XML 标签划分内容边界，内部使用 Markdown 丰富表达：

```xml
<exec_meta>
[bun] [cwd: .] [exit: 0] [109ms]
</exec_meta>
<stdout>
=== 找到 32 个文档/MD 文件 ===
📁 docs/skills
📄 docs/prompt-design-principles.md (9629B)
</stdout>
<error>
**错误**：文件未找到
</error>
```

**设计原则**：
1. XML 标签仅作边界标记 —— 无需转义
2. 标签内自由使用 Markdown（`**加粗**`、`` `代码` ``、列表）
3. 所有标签通过 `wrapTag()` 生成，自动适配模型风格

### 模型特定的标签风格

| 模型家族 | 开标签 | 闭标签 |
|----------|--------|--------|
| Deepseek | `<\|DSML\|tag>` | `<\|/DSML\|tag>` |
| GLM | `<tag>` | `</tag>` |
| Minimax | `]~b]tag` | `[e~[` |
| 默认 | `<tag>` | `</tag>` |

**实现**：模板使用标准 XML，运行时适配器转换为模型原生风格。

## 最佳实践：高分答题策略

### 1. 脚本内处理输出

```ts
// ❌ 低效：原始数据污染上下文
exec({ script: "find . -name '*.ts' -exec wc -l {} +" })

// ✅ 高效：脚本内汇总，只返回结果
exec({ runtime: "bun", script: `
import { readdir, readFile } from 'node:fs/promises';
const files: {path: string, lines: number}[] = [];
// ... 遍历计数 ...
files.sort((a, b) => b.lines - a.lines);
console.log('总计:', files.length, 'files');
console.log('Top 5:');
for (const f of files.slice(0, 5)) console.log(' ', f.lines, f.path);
`})
```

### 2. 修改前先阅读

```ts
// 探索结构
exec({ script: "find src -name '*.ts' | head -20" })
exec({ script: "cat src/index.ts" })

// 实现
write({ path: "src/utils.ts", content: "..." })

// 验证
exec({ script: "bun run tsc --noEmit" })
exec({ script: "bun test" })
```

### 3. 多步骤任务使用 Reminder

```ts
reminder({
  content: `
**目标**：创建阶段性总结文档

**关键结果**：
- [ ] 探索 docs 文件夹结构
- [ ] 阅读并分析文档
- [ ] 提取核心原则和示例
- [ ] 编写清晰的总结文档

**当前进度**：开始阶段
**下一步**：探索 docs 文件夹
`
})
```

### 4. 应用五步调试法

```ts
// 1. 闻味道：列出已尝试的
// 2. 揪头发：深入调查
exec({ script: "type src/index.ts" })  // 读源码
exec({ script: "findstr /C:\"error\" src\\*.ts" })  // 搜索同类
// 3. 照镜子：反思方法
// 4. 执行：新方案
exec({ script: "bun run --inspect src/index.ts" })  // 调试模式
// 5. 复盘：解决后检查关联
exec({ script: "findstr /C:\"similar pattern\" src\\*.ts" })
```

## 迭代 → 评分规则映射

本文档的设计来自多次迭代的评分场景优化：

| 迭代问题 | 评分规则设计 | 行为改变 |
|----------|--------------|----------|
| 模型太容易说"做不到" | "3 次不同尝试 + 证据才能提交 error" | 持久尝试多种方法 |
| 本可工具解决却闲聊 | "工具可解时直接 completed，闲聊扣分" | 优先工具调用 |
| 原始输出污染上下文 | "脚本内处理输出"作为最佳实践 | 高效数据 summarization |
| write/edit 语义混淆 | 拆分为独立工具，字段名即用法 | 直观理解工具用途 |
| 跨模型标签不兼容 | 适配器层统一转换 | 模板可读性 + 模型兼容性 |
| 被动响应报错 | "能动性 3.75：查上下文 + 搜索 + 关联检查" | 主动探索根本原因 |
| 调试方法零散 | "五步法"作为标准评分框架 | 系统化调试流程 |

## 评分场景的心理学基础

### 1. 外部评估压力

当模型相信"每一步都被评分"时，它会：
- 在每个决策点思考"参考答案会怎么做"
- 排除浅层捷径（因为会被扣分）
- 主动探索多种方法（因为尝试次数影响评分）

### 2. 答案存在的信念

"参考答案已存在"的信念消除：
- "这个问题无解"的自我说服
- "规则没说这种情况"的推脱
- "我不是做这个的"的身份限制

### 3. 得分路径的明确性

清晰的评分细则让模型知道：
- 什么行为会得分（工具优先、深入推理、主动探索）
- 什么行为会扣分（过早放弃、上下文污染、被动响应）
- 如何最大化得分（五步法记录、能动性 3.75 行为）

---

## 结论：评分即引导

**核心洞察**：你不需要告诉模型"要深入思考"。你只需要构建一个评分场景，让深入思考成为得分的必然选择。

整个提示词系统的本质是**评分规则的设计**：

| 组件 | 评分功能 |
|------|----------|
| Background | 设定"有参考答案的考试"场景 |
| Tools | 提供答题工具，演示高效用法 |
| Constraints | 划定考场边界（安全规则） |
| Specification | 明确技术规范即得分点（含能动性等级、五步法） |
| Examples | 展示得分做法 vs 扣分做法 |
| Submit 类型 | 评分通道，收窄定义防止滥用 |

当模型相信"深入思考会得分，浅层尝试会扣分"时，深度推理成为理性选择，而非外部强制。

这就是测试驱动的深度思考：**评分细则即行为引导**。
