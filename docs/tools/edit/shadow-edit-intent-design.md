## 2. 核心架构确认

### 分工模型

```
主模型（贵、强、统揽全局）
  → 自然语言意图（语义定位 + 变换描述）
Editor LLM（便宜、快、专注翻译 + 反馈）
  → 输入：系统提示 + 源文件 + 意图（大部分可 prefix cache）
  → 输出：编辑结果 + 反馈
确定性执行引擎
  → apply + diff + 验证 → 结果返回主模型
```

关键经济学事实：Editor LLM 是廉价小模型（甚至自部署），系统提示+源文件大部分可缓存，多次重试的成本远低于主模型重试一次。

### 主模型不需要表达 anchor

主模型不需要：
- 精确复制原始代码片段（最容易出错的操作）
- 使用行号定位（LLM 的已知弱点）
- 描述"原来是什么样子"（源文件里已经有了）

主模型只需要用自然语言描述**要改成什么**，定位工作完全交给 Editor LLM。

## 3. 意图表达的二维图谱

### 维度定义

**定位精度（H(where)）**：

| 级别 | 描述 | 示例 |
|------|------|------|
| W1: 行号 | 精确坐标 | "第 42-48 行" |
| W2: 内容锚点 | 精确引用原文片段 | "把 `case blackfriday.CodeBlock:` 开始的分支" |
| W3: 语义描述 | 用语义/结构描述位置 | "CodeBlock 的 case 分支" |
| W4: 隐式 | 不显式定位，从变换意图中推断 | "加个 entering 检查" |

**变换精度（H(what)）**：

| 级别 | 描述 | 示例 |
|------|------|------|
| T1: 完整目标代码 | 直接给出修改后的代码 | "替换为 `if entering { ... }`" |
| T2: 操作+关键内容 | 描述操作类型+关键变化 | "在开头添加 `if !entering { return }` 守卫" |
| T3: 语义意图 | 描述期望的行为变化 | "添加 entering 检查，只在 entering=true 时处理" |
| T4: 目标描述 | 只描述期望结果 | "修复重复处理的 bug" |

### 图谱评估

```
变换精度 →   T1(完整代码)    T2(操作+关键)   T3(语义意图)    T4(目标描述)
定位精度↓
W1(行号)      过度指定        收益≠成本       不协调          严重不协调
W2(锚点)      理论最优/       改善有限        不划算          最差组合
              实践次优
W3(语义)      ⭐甜蜜点A      ⭐甜蜜点B       条件适用        超出范围
W4(隐式)      不稳定          风险偏高        不适合精确编辑   不是编辑指令
```

### 甜蜜点

**W3×T1（语义定位 + 完整目标代码）**：主模型已知目标代码时的最优选择。零变换歧义，定位由 Editor LLM 语义理解完成。

**W3×T2（语义定位 + 操作+关键内容）**：修改较简单时的最优选择。Editor LLM 补全细节的任务在能力范围内。

主模型自然会根据编辑复杂度在这两个甜蜜点之间滑动，不需要强制选择。

## 4. 运行时反馈机制

### 核心设计

Editor LLM 不仅执行编辑，还返回**反馈**评估主模型的指令质量：

| 反馈类型 | 触发条件 | 反馈内容 | 效果 |
|---------|---------|---------|------|
| **过度指定** | 检测到行号、精确代码复制等 | "你不需要提供行号/原始代码，用语义描述即可" | 引导从 W1/W2 → W3 |
| **任务过大** | 单次意图涉及多处不相关修改 | "建议拆分为 N 个独立编辑" | 解决粒度问题 |
| **过于模糊** | 无法唯一定位或无法确定变换 | "无法确定修改位置，请更具体地描述" | 防止滑向 W4/T4 |

反馈机制本质上是在运行时将主模型的表达方式**推向甜蜜点区域**。

### 价值

1. **去除庞杂的静态工具说明**：工具 prompt 可以极度精简（一句话描述 + 简单示例），主模型通过运行时反馈动态学习最优调用模式
2. **降低成本**：将"简单但庞杂的判断"（指令是否过于复杂/过大/过于模糊）迁移到便宜模型处理，减少主模型的心智负担和 token 消耗
3. **适应性**：不同模型、不同场景收到不同反馈，自然收敛到各自最优模式
4. **可演化**：改进 Editor LLM 的反馈逻辑即可改进所有主模型的使用模式

### 工具接口

```
shadow_edit(path, intent): 编辑文件。用自然语言描述你的修改意图。

示例：
  shadow_edit("src/handler.go", "在 handleRequest 函数开头添加参数校验，如果 req.Body 为 nil 则返回 400 错误")
```

仅需简单示例作为引导，减少前期试错。后续通过 Editor LLM 反馈动态优化。

## 5. 与方案 A（{anchor, replacement}）的关系

方案 B（shadow edit）在精确端退化为方案 A：当主模型的意图是"将 X 替换为 Y"时，Editor LLM 只是做格式翻译。两者是连续谱的不同位置，不是对立方案。

shadow edit 的优势在于：主模型可以在连续谱上自由滑动，而 Editor LLM + 反馈机制确保无论主模型在哪个位置表达，都能得到正确执行或有效纠正。

## 6. 架构演进：editorLoop

### 问题

初版实现中 `resolveAndApply()` 是一个手写的 mini agent loop（~150 行），与 `@n0n/core` 的 `agentLoop` 高度重复。
考虑复用 `agentLoop`，但会导致 `@n0n/tools → @n0n/core` 的循环依赖（当前依赖链：`types ← llm/tools ← core`）。

### 决策

Editor LLM 是 edit 工具的**内部实现细节**，不应泄漏到外部。在 `edit.ts` 内部实现专用的 `editorLoop`，完全封装，只依赖 `@n0n/llm`。

### Editor LLM 工具集

| 工具 | 参数 | 职责 |
|------|------|------|
| `str_replace` | `old_string`, `new_string` | 单次精确替换，可多次调用 |
| `view_file` | 无 | 读取当前文件状态 |
| `submit` | `feedback?` | 提交完成 + 可选反馈，退出循环 |

设计理由：
- **`str_replace`**：扁平参数，符合模型先验（Anthropic `edit_file` 模式），单次调用单次替换
- **`view_file`**：多次编辑后确认当前状态，比在错误消息中塞完整文件更干净
- **`submit`**：统一退出机制 + 反馈通道，指令清晰时直接 submit 不带 feedback
- **不给 exec**：Editor LLM 职责是翻译编辑意图为文本替换，不需要执行脚本
